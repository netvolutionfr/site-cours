$fillable devient un attribut PHP

use Illuminate\Database\Eloquent\Attributes\Fillable;

#[Fillable(['titre', 'destination', 'depart',
            'prix', 'places'])]
class Voyage extends Model {}
  • Remplace protected $fillable = [...], encore accepté
  • #[...] : attribut PHP 8, métadonnée lue par Laravel
  • Liste blanche de create(), pas une validation

Essayons de casser l’API

curl -s -X POST http://127.0.0.1:8000/api/voyages \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"titre":"Test","destination":"Lune",
       "depart":"2020-01-01","prix":-50,"places":0}'

Réponse 201 : le voyage absurde est enregistré. Avec un titre vide : 500.

Le navigateur ne protège rien

  • required, min, type="date" : du confort pour l’utilisateur
  • curl, une appli mobile, un script : ils ne passent pas par le formulaire
  • La validation qui protège s’exécute sur le serveur

Ne jamais faire confiance à une donnée qui vient du client.

Les règles métier, écrites une fois

public function rules(): array
{
    return [
        'titre' => ['required', 'string', 'max:120'],
        'destination' => ['required', 'string', 'max:100'],
        'depart' => ['required', 'date', 'after:today'],
        'prix' => ['required', 'numeric', 'gt:0'],
        'places' => ['required', 'integer', 'between:1,60'],
    ];
}

Chaque ligne traduit une contrainte du tableau de conception.

Une règle, deux clients, deux réponses

Le contrôleur ne voit que du valide

public function store(VoyageRequest $request)
{
    $voyage = Voyage::create($request->validated());

    return response()->json($voyage, 201);
}
  • VoyageRequest : validation avant l’appel
  • validated() : seulement les champs prévus, un "id": 999 est ignoré

Les quatre mécanismes d’un formulaire

Élément Rôle
@csrf Jeton de session ; sans lui, 419
@method('PUT') Simule PUT ou DELETE, que HTML ne connaît pas
@error('prix') Affiche l’erreur du champ dans $message
old('prix', $voyage->prix) Rend la saisie refusée, sinon la valeur enregistrée

Source, sink : où naît une faille

  • Source : toute donnée contrôlée par le client — formulaire, JSON, URL, en-tête, base
  • Sink : l’endroit où elle est interprétée — HTML, SQL, redirection, commande
  • Faille : une source atteint un sink sans traitement adapté au contexte

Valider en entrée (le métier), échapper en sortie (le contexte).

Le JSON du 201 n’est pas un sink : c’est le client qui l’affichera qui doit échapper.

Cinq sinks triviaux en Laravel

XSS stockée
  {!! $v->titre !!}              →  {{ $v->titre }}
XSS côté client
  el.innerHTML = v.titre         →  el.textContent = v.titre
Injection SQL
  whereRaw("destination = '$d'") →  where('destination', $d)
Redirection ouverte
  redirect($request->retour)     →  to_route('voyages.index')
Affectation de masse
  #[Unguarded] + all()           →  #[Fillable] + validated()
