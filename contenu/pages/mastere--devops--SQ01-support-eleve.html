1. Culture DevOps et diagnostic

Le cycle, rappel de la présentation du module

DevOps réunit ceux qui développent une application et ceux qui l’exploitent autour d’une même chaîne, automatisée autant que possible, et d’une responsabilité partagée sur le résultat en production.

Étape Question Outil dans ce module
Coder Comment travailler à plusieurs sur le même code ? Git, GitHub, pull requests
Construire L’application tourne-t-elle partout de la même façon ? Docker, Docker Compose
Tester Une modification casse-t-elle l’existant ? Tests Laravel, GitHub Actions
Déployer Comment livrer sans geste manuel risqué ? GitHub Actions, Kubernetes (k3d)
Décrire l’infrastructure Comment recréer un environnement à l’identique ? Terraform
Surveiller Comment savoir qu’elle tombe avant les utilisateurs ? Journaux, contrôle de disponibilité, alerte

Tout commence par la première ligne : une chaîne automatique ne vaut que si le code qui y entre est intégré proprement. C’est l’objet de la partie 2.

Pourquoi DevOps

Développement et exploitation ont longtemps eu des objectifs opposés : livrer du nouveau d’un côté, éviter les pannes de l’autre. Le code était « jeté par-dessus le mur » ; les livraisons, rares, devenaient grosses et risquées. Le mouvement DevOps naît en 2009 (conférence Velocity, premiers DevOpsDays à Gand) pour réunir les deux métiers autour d’une chaîne commune. Ses piliers se résument par CALMS : culture de responsabilité partagée, automatisation, petits lots livrés souvent (lean), mesure, partage des outils et des connaissances.

Trois niveaux d’automatisation

Pratique Ce qui est automatique Ce qui reste humain
Intégration continue (CI) Chaque modification fusionnée est construite et testée La revue de code
Livraison continue Chaque version validée est prête à partir en production La décision de livrer
Déploiement continu (CD) Chaque version validée part en production Rien dans la chaîne ; la surveillance prend le relais

Mesurer : les quatre indicateurs DORA

Indicateur Mesure Famille
Fréquence de déploiement Nombre de livraisons en production sur une période Rapidité
Délai de mise en production Temps entre un commit et sa présence en production Rapidité
Taux d’échec des changements Part des livraisons qui provoquent un incident Stabilité
Temps de rétablissement Durée pour revenir à un service normal après un incident Stabilité

Les études DORA (Accelerate, 2018) montrent que les équipes les plus performantes progressent sur les deux familles à la fois : livrer souvent, par petits lots, rend chaque livraison moins risquée.

2. Collaborer avec Git et GitHub

Le problème

Ce matin, trois personnes ont travaillé sur trois branches du même dépôt. Deux d’entre elles ont modifié les mêmes fichiers (routes/web.php, VoyageController.php, index.blade.php). Il faut maintenant tout réunir dans main, sans perdre le travail de quiconque et sans jamais laisser main dans un état cassé.

Le GitHub flow

Règle Raison
main fonctionne toujours C’est elle qui sera testée, construite et déployée automatiquement.
Une branche courte par changement Moins elle vit longtemps, moins elle diverge de main.
Toute fusion passe par une pull request (PR) La PR est le lieu de la discussion, de la revue et, bientôt, des tests automatiques.
Une approbation au moins avant fusion Deux personnes au moins comprennent chaque ligne livrée.
La branche est supprimée après fusion Son histoire est désormais dans main.

Le Gitflow des supports de l’an dernier ajoute une branche develop et des branches de version. Il convient à des livraisons espacées et numérotées ; pour une petite équipe qui livre en continu, le GitHub flow suffit et laisse moins de branches à synchroniser.

Protéger main

L’enseignant, propriétaire du dépôt, crée la règle en direct : Settings → Rules → Rulesets → New branch ruleset, cible Default branch, avec :

  • Restrict deletions et Block force pushes ;
  • Require a pull request before merging, Required approvals : 1.

Le dépôt est public : avec un compte GitHub gratuit, ces règles ne s’appliquent qu’aux dépôts publics. Le code ne contient aucun secret, puisque .env reste hors du dépôt.

Vérifiez la règle. Sur votre poste, sur main, faites un commit sans importance et tentez git push. Le refus doit mentionner une violation de règle du dépôt. Annulez ensuite ce commit local avec git reset --hard origin/main.

Ouvrir sa pull request

Votre branche a été publiée ce matin (git push -u origin <branche>). Sur GitHub, ouvrez une PR de votre branche vers main. Sa description suit ce modèle :

## Quoi
Ce que la branche ajoute, en deux ou trois phrases.

## Pourquoi
Le besoin ou le problème réglé.

## Comment tester
Les commandes et les gestes pour vérifier,
y compris une saisie invalide.

Relire la pull request d’un autre

Chacun relit une PR, en cercle : API relit Création, Création relit Modification, Modification relit API. Récupérez la branche pour la tester réellement :

git fetch origin
git switch feature/creation-voyage
php artisan migrate
php artisan serve

Dans l’onglet Files changed de la PR, vérifiez :

  • le code fait ce qu’annonce la description, et le test décrit fonctionne ;
  • vous comprenez chaque ligne, sinon vous posez la question ;
  • aucun fichier n’est en trop : .env, vendor/, base SQLite, fichiers d’éditeur ;
  • les noms de variables, routes et vues sont explicites et cohérents avec le reste.

Un commentaire utile tient en trois temps : constat, raison, proposition.

« store() utilise $request->all() : un champ non prévu serait enregistré. Proposition : $request->validated(), comme dans l’API. »

Terminez par Review changes : Request changes pour au moins un point justifié, puis Approve quand l’auteur l’a corrigé. La correction se fait par un nouveau commit sur la même branche : la PR se met à jour toute seule.

Fusionner, puis résoudre un conflit

Ordre de fusion du premier tour : 1. API, 2. Création, 3. Modification. Après chaque fusion, chacun met à jour son main local avec git switch main puis git pull.

Quand vient son tour, la PR « Modification » affiche This branch has conflicts that must be resolved : main a reçu la Création, qui a touché les mêmes lignes. On intègre main dans la branche, sur son poste, pour pouvoir tester le résultat :

git switch feature/modification-voyage
git fetch origin
git merge origin/main
CONFLICT (content): Merge conflict in routes/web.php
Automatic merge failed; fix conflicts and then commit the result.

Git a fusionné tout ce qu’il pouvait et a laissé, dans chaque fichier en conflit, les deux versions des lignes concurrentes :

<<<<<<< HEAD
Route::get('/voyages/{voyage}/edit', ...);
Route::put('/voyages/{voyage}', ...);
Route::delete('/voyages/{voyage}', ...);
=======
Route::get('/voyages/create', ...);
Route::post('/voyages', ...);
>>>>>>> origin/main

HEAD désigne votre branche ; la partie après ======= vient de main. Résoudre, ce n’est pas choisir un camp : c’est écrire la version qui respecte les deux intentions. Ici, garder les cinq routes ; ailleurs, garder un seul exemplaire d’un bloc ajouté des deux côtés, comme l’affichage du message flash.

  1. git status liste les fichiers en conflit.
  2. Éditez chacun : version finale écrite, marqueurs <<<<<<<, =======, >>>>>>> supprimés.
  3. Testez : php artisan route:list --path=voyages, puis liste, création, modification et suppression dans le navigateur.
  4. git add des fichiers résolus, puis git commit pour conclure la fusion.
  5. git push : la PR redevient fusionnable.

Lisez enfin l’histoire produite :

git log --oneline --graph --all

Second tour : de l’issue à la fusion

L’enseignant a ouvert trois issues sur le dépôt. Chacune fait l’objet d’une branche, d’une PR qui contient Closes #<numéro> dans sa description, et d’une revue dans le même cercle.

Issue Prise par Indication
Afficher le départ au format français (15/03/2027) Modification $voyage->depart->format('d/m/Y')
Afficher le prix en euros (420,00 €) API number_format($voyage->prix, 2, ',', ' ')
Afficher les places, et « Aucun voyage prévu » si la liste est vide Création @forelse … @empty … @endforelse

Ordre de fusion : Modification, API, Création. Les trois issues touchent des lignes voisines de la liste : à ce tour, l’API puis la Création intègrent main et résolvent leur conflit. À la fin de l’après-midi, chacun en a donc résolu un.

Critère de réussite : chacun a ouvert une PR relue, demandé une modification argumentée et résolu un conflit ; main contient toutes les fonctions et l’application démarre depuis un clone neuf.

Restitution

Chacun, sur son poste projeté :

  1. présente sa PR : description, commentaire reçu, commentaire donné ;
  2. montre son conflit : les deux versions, celle retenue et pourquoi ;
  3. commente git log --oneline --graph autour de sa fusion.

Pour finir, l’enseignant clone le dépôt dans un dossier neuf et installe l’application devant l’équipe. Comptez les commandes nécessaires et notez ce qui pourrait différer d’un poste à l’autre : version de PHP, extensions, base de données. C’est le problème de l’intervention 3.

Extensions

  • Annuler une fusion fautive. Sur une branche, git revert -m 1 <commit-de-fusion>, puis PR. Pourquoi ne pas réécrire l’histoire de main à la place ?
  • Marquer une version. git tag -a v0.1.0 -m "Liste, API et formulaires", puis git push origin v0.1.0, et une release GitHub qui résume les PR fusionnées.
  • Modèle de PR. Placez le modèle de description dans .github/pull_request_template.md, par une PR : GitHub le proposera à chaque nouvelle PR.

3. Conteneuriser l’application

Le problème

Le clone neuf de la partie 2 a demandé une dizaine de commandes et suppose, sur chaque poste, la bonne version de PHP, les bonnes extensions, Composer, une base et un .env. Un conteneur embarque le système et les dépendances de l’application : le démarrage ne dépend plus du poste.

Terme Ce que c’est
Image Un modèle en lecture seule, fait de couches empilées : système, extensions, dépendances, code.
Conteneur Une instance de l’image qui s’exécute. On le supprime et on le recrée sans regret.
Registre Le dépôt où l’on publie et récupère des images : Docker Hub, GitHub Container Registry.
Volume Un stockage géré par Docker, qui survit à la suppression du conteneur.

Contrairement à une machine virtuelle, un conteneur n’embarque pas de système complet : il partage le noyau de l’hôte, démarre en quelques secondes et pèse bien moins lourd.

Vérifier l’installation

docker --version
docker compose version
docker run --rm hello-world

La dernière commande télécharge une image, lance un conteneur qui affiche un message, puis le supprime (--rm). Si elle échoue, Docker Desktop n’est pas démarré.

Le Dockerfile

À la racine du dépôt, le fichier Dockerfile décrit la construction de l’image :

FROM php:8.3-apache

RUN apt-get update \
    && apt-get install -y --no-install-recommends git unzip libzip-dev \
    && docker-php-ext-install pdo_mysql zip \
    && a2enmod rewrite \
    && rm -rf /var/lib/apt/lists/*

ENV APACHE_DOCUMENT_ROOT=/var/www/html/public
RUN sed -ri -e 's!/var/www/html!${APACHE_DOCUMENT_ROOT}!g' \
    /etc/apache2/sites-available/*.conf
RUN sed -ri -e 's!/var/www/!${APACHE_DOCUMENT_ROOT}!g' \
    /etc/apache2/apache2.conf /etc/apache2/conf-available/*.conf

COPY --from=composer:2 /usr/bin/composer /usr/bin/composer
WORKDIR /var/www/html

COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --no-autoloader --prefer-dist

COPY . .
RUN composer dump-autoload --optimize \
    && chown -R www-data:www-data storage bootstrap/cache
Instruction Rôle
FROM php:8.3-apache Part de l’image officielle PHP 8.3 avec Apache, à une version écrite.
RUN … docker-php-ext-install Ajoute les extensions PHP nécessaires : pdo_mysql pour MariaDB, zip pour Composer.
a2enmod rewrite Active la réécriture d’URL, nécessaire aux routes Laravel.
APACHE_DOCUMENT_ROOT et sed Fait servir le dossier public/ : le reste du projet n’est pas accessible par le web.
COPY --from=composer:2 Récupère l’exécutable Composer depuis son image officielle.
COPY composer.json composer.lock puis composer install Installe exactement les versions verrouillées. Copiés avant le code, ces fichiers permettent à Docker de réutiliser la couche vendor/ tant qu’ils ne changent pas.
COPY . . Copie le code, sauf ce que .dockerignore exclut.
chown Laisse Apache écrire dans storage/ et bootstrap/cache/.

À côté, le fichier .dockerignore liste ce qui ne doit pas entrer dans l’image :

.git
.env
vendor
node_modules
database/*.sqlite

compose.yaml

Le fichier compose.yaml décrit les deux services et leur liaison :

services:
  app:
    build: .
    ports:
      - "8000:80"
    env_file: .env
    environment:
      DB_CONNECTION: mariadb
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy

  db:
    image: mariadb:11.4
    environment:
      MARIADB_DATABASE: ${DB_DATABASE}
      MARIADB_USER: ${DB_USERNAME}
      MARIADB_PASSWORD: ${DB_PASSWORD}
      MARIADB_RANDOM_ROOT_PASSWORD: "1"
    volumes:
      - db_data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 5s
      retries: 10

volumes:
  db_data:
  • "8000:80" : le port 8000 de l’hôte mène au port 80 du conteneur app. La base n’a pas de ports : elle n’est joignable que depuis le réseau interne.
  • DB_HOST: db : sur ce réseau, chaque service est joignable par son nom.
  • env_file: .env : les variables du .env sont injectées au démarrage. Une variable d’environnement l’emporte sur le fichier .env lu par Laravel : DB_CONNECTION et DB_HOST remplacent donc les valeurs SQLite du poste.
  • ${DB_DATABASE} : Compose lit aussi le .env placé à côté de compose.yaml pour compléter le fichier. Un seul .env configure ainsi Laravel et MariaDB.
  • depends_on avec service_healthy : app attend que la base réponde vraiment, pas seulement que son conteneur existe.

Attention

MariaDB n’utilise MARIADB_DATABASE, MARIADB_USER et MARIADB_PASSWORD qu’au premier démarrage, sur un volume vide. Changer le mot de passe ensuite ne change rien : il faut supprimer le volume (docker compose down -v), et donc les données.

Démarrer

Dans votre .env (jamais commité), décommentez et renseignez les variables de base, par exemple DB_DATABASE=voyages, DB_USERNAME=voyages et un mot de passe. Reportez ces noms, sans valeur secrète, dans .env.example. Puis :

docker compose up -d --build
docker compose ps
docker compose exec app php artisan migrate --seed

Ouvrez http://localhost:8000/voyages et http://localhost:8000/api/voyages.

Commande Effet
docker compose logs -f app Suit les journaux d’Apache et de Laravel.
docker compose exec app sh Ouvre un terminal dans le conteneur app.
docker compose down Arrête et supprime les conteneurs ; le volume db_data est conservé.
docker compose down -v Supprime aussi les volumes : les données sont perdues.
Symptôme Premier contrôle
port is already allocated Un php artisan serve tourne encore ? Sinon, "8001:80".
Page 500, No application encryption key APP_KEY est-il renseigné dans .env ?
Erreur sur la table sessions Les migrations ont-elles été lancées dans le conteneur ?
Connection refused vers la base DB_HOST=db ; docker compose ps montre-t-il db healthy ?
Access denied for user Identifiants changés après le premier démarrage : down -v.
Permission denied dans storage/ Le chown du Dockerfile a-t-il été exécuté ?

À trois : conteneuriser par pull request

Chacun crée une branche depuis main à jour, ouvre une PR et relit celle de son voisin, comme en partie 2. Les trois PR sont nécessaires pour que la pile démarre : fusionnez-les, puis testez.

  1. API : Dockerfile et .dockerignore. Construisez l’image seule avec docker build -t voyages-app . et expliquez dans la PR chaque instruction.
  2. Création : compose.yaml et .env.example complété des variables de base. Vérifiez la syntaxe avec docker compose config, sans coller la sortie dans la PR : elle contient les valeurs du .env.
  3. Modification : section « Démarrer avec Docker » du README.md (prérequis, commandes, adresse, arrêt). Après les fusions, clonez le dépôt dans un dossier neuf et suivez le README à la lettre.

Critère de réussite : depuis un clone neuf, cp .env.example .env, la clé, les variables de base, docker compose up -d --build et la migration suffisent à afficher la liste et l’API.

Questions

  1. Après docker compose down puis up -d, les voyages sont-ils toujours là ? Et après down -v ? Expliquez.
  2. Pourquoi l’URL de la base est-elle db et non 127.0.0.1 dans le conteneur app ?
  3. On remplace FROM php:8.3-apache par FROM php:apache. Quel risque cela fait-il courir à la reproductibilité ?
  4. Pourquoi copier composer.lock avant le reste du code ? Observez la durée d’un second docker compose build après avoir modifié une vue.
  5. Citez deux pratiques du Dockerfile qui garantissent que deux postes obtiennent le même résultat.

Extensions

  • Utilisateur non privilégié. Recherchez pourquoi un conteneur qui s’exécute en root est un risque, et ce que fait déjà l’image php:apache pour les processus Apache.
  • Épingler par empreinte. docker images --digests affiche l’empreinte sha256 d’une image ; FROM php:8.3-apache@sha256:… fige l’image au bit près. Quel inconvénient pour les correctifs de sécurité ?

Second tour

Ligne du tableau après les trois fusions :

<td>{{ $voyage->depart->format('d/m/Y') }}</td>
<td>{{ number_format($voyage->prix, 2, ',', ' ') }} €</td>
<td>{{ $voyage->places }}</td>

La boucle devient @forelse ($voyages as $voyage), suivie de @empty et d’une ligne « Aucun voyage prévu » avant @endforelse ; l’en-tête reçoit une colonne « Places ».

Extension : annuler une fusion

git revert crée un nouveau commit qui défait la fusion : l’histoire de main reste intacte pour toute l’équipe et la règle de protection est respectée. Réécrire l’histoire (reset puis push --force) est bloqué par la règle et désynchroniserait les clones des autres.

Partie 3 — Questions

  1. Après down puis up, les voyages sont toujours là : les conteneurs sont recréés, mais la base écrit dans le volume nommé db_data, qui n’est pas supprimé. down -v supprime le volume : la base repart vide, il faut relancer la migration.
  2. Dans le conteneur, 127.0.0.1 désigne le conteneur app lui-même, où aucune base n’écoute. Compose crée un réseau où chaque service est résolu par son nom : db désigne le conteneur MariaDB.
  3. php:apache suit la dernière version de PHP publiée : une construction de demain peut embarquer une version plus récente de PHP et casser l’application, alors que le code n’a pas changé. Deux postes qui construisent à des dates différentes n’obtiennent plus la même image.
  4. Chaque instruction produit une couche, réutilisée si ses entrées n’ont pas changé. Tant que composer.json et composer.lock sont identiques, la couche composer install vient du cache : modifier une vue ne relance que COPY . . et la suite, en quelques secondes.
  5. Par exemple : une image de base à version figée (php:8.3-apache, jamais latest) ; des dépendances installées depuis composer.lock commité ; un .dockerignore qui exclut vendor et .env, pour que rien du poste n’entre dans l’image.
